# OpenStaffs 组织架构与作用域统一声明 设计

> 状态：待评审 · 日期：2026-10-18 · 版本：v2（整体重构版）· 分支：（实现时定）
> 关联：`2026-10-16-openstaffs-architecture-design.md`（**修订** §4.1「员工扁平、组织由群聊表达」与 §非目标「独立组织架构层」）、`2026-10-16-openstaffs-permissions-design.md`（**扩展**写权限判定）、`2026-10-17-permission-request-design.md`（授权弹框链路）
> 性质：**破坏性重构**。覆盖三件事：**① 组织架构（部门树 + 负责人）；② 项目负责人（群主）；③ 全作用域统一声明**。

---

## 1. 背景与目标

现状（master）：

- `agents/<id>/` **扁平**；员工 = 一个自包含文件夹（`AGENTS.md` + `profile.md` + `MEMORY.md` + `config.json` + `skills/` + `mcp.json` + `permission.json`）。
- 组织关系**由群聊表达**（架构设计 §4.1 决策）。
- 项目（群聊）无负责人；`prompt / skills / mcp / permissions` 四类能力在**各层格式各异、处理各异**（`AGENTS.md` / `skills/` 目录 / `mcp.json` / `permission.json`，四套机制）。

本设计三件事：

1. **组织架构**：文件夹 = 部门（可嵌套），`<名字>.agent.json` = 人；部门/项目均可有**可选负责人**，管理权由结构 + 负责人推出。
2. **项目负责人（群主）**：与部门主管**完全同构**。
3. **统一声明**：`prompt / skills / mcp / permissions` 四类收敛为**同一种声明格式**，**全作用域（系统/空间/项目/组织/员工）统一**，由**一套解析器**沿作用域链合并。

**一句话**：*文件夹是部门、文件是人；负责人可选、只管本级成员；四类能力一种形状、一套处理；读全透明。*

**非目标（本设计不覆盖）：**

- **能力覆盖优先级**（组织链 vs 项目 vs 员工，谁赢）——**标记待定**，实现前再定（§7、§10）；
- 读限制（明确**不做**，读零限制）；
- 硬档隔离 / 容器（沿用现有软边界）；
- 群内模式（`@` 前缀块、组队等）的改动。

| D2 | **人由单一 JSON 定义** | 原 `AGENTS.md`/`profile.md`/`config.json`/`mcp.json`/`permission.json` 并入该 JSON；技能改为**引用**；记忆移到工作树（`work/<id>/memory.md`） |
| D3 | **部门声明 = `department.json`** | `{ alias, head?, prompt?, skills?, mcp?, permissions? }` |

| D9 | **统一处理** | **一套解析器**沿"作用域链"合并出会话最终能力（各类型合并语义见 §7） |
| D10 | **`prompt` = 内联字符串** | 声明里直接内联多行文本；**取消所有层级的 `AGENTS.md`** |
| D11 | **`org.json` 不需要** | 目录层级（+ `department.json`）即组织 |
| D12 | **写权限 = 默认两项 ∪ 继承** | ① 自己工作空间 `work/<自己>/`；② 自己**作为管理者时**，其**管理子树**内的部门声明与人声明；③ 继承：祖先部门声明的 `permissions` |

| D17 | **根部门可选；老板最高** | `agents/department.json` 缺省即无公司别名；老板全可写；现有 `request_permission`（向老板申请）保留 |

## 3. 目录结构

```
<办公空间>/
├─ agents/                        # 组织：定义树（文件夹 = 部门；可任意嵌套）
│  ├─ department.json             # 根部门（可选）
│  └─ eng/
│     ├─ department.json          # 部门声明（含可选 head）
│     ├─ alice.agent.json         # 人
│     ├─ dave.agent.json
│     └─ platform/
│        ├─ department.json
│        ├─ bob.agent.json
│        └─ carol.agent.json
├─ projects/                      # 协作：群聊
│  └─ demo/
│     ├─ project.json             # 群声明（含可选 owner、成员、prompt/能力/权限）
│     ├─ data/                    # 共享工作区
│     └─ conversation_ids/
├─ work/                          # 工作树（平铺）
│  ├─ alice/                      # 工作产出 + memory.md
│  └─ bob/  carol/  dave/  eng/…
└─ openstaffs/                    # 空间级附属与共享库
   ├─ skills/                     # 共享技能库（被声明引用）
   ├─ mcp.json                    # 空间级 MCP
   └─ <空间声明>                  # 空间作用域声明（落点/文件名待定，§10）
```

- 定义树：**只有 `department.json`（部门声明）与 `<名字>.agent.json`（人）两类文件**；其余是子部门文件夹。
- 系统作用域声明由框架内置（`src/`），非用户编辑。

## 4. 统一声明字段

**同一种形状**，五层（系统 / 空间 / 项目 / 组织 / 员工）通用：

| 字段 | 类型 | 含义 |
|---|---|---|
| `prompt?` | string（内联） | 该作用域贡献的提示词片段（D10） |
| `skills?` | string[] | 技能引用（见 §10 引用语法） |
| `mcp?` | 内联定义（见 §10） | MCP server |
| `permissions?` | string[] | 该作用域贡献的额外写权限（沿链累积） |

**各层声明载体（草案，待定）**：

| 作用域 | 载体 |
|---|---|
| 系统 | 框架内置（`src/`） |
| 空间 | `openstaffs/` 下某文件（待定） |
| 项目 | `projects/<id>/project.json`（+ 成员名单，落点待定 §10） |
| 组织 | `department.json`（+ 可选 `head`） |
| 员工 | `<名字>.agent.json` |

## 5. 负责人与管理权

**负责人（可选）**

- 部门：`department.json.head`；项目：群声明 owner。**只能选本级成员**；匹配不到即**无**。
- 主管不能写自己的 `agent.json`（D6）。

**管理权（D5，主管制 + 穿透）**

> 对任一部门 / 人 **X**：沿 X 的祖先链（含其自身所在部门）向上找**最近的、有 `head` 的部门** D；**D 的主管**即 X 的管理者。全链无 → **老板**。管理者的权限覆盖**其所在部门的整棵子树**（部门 + 人，**任意深度**）。

- 一个主管可管到**孙级及更深**的部门与人（穿透）。
- **同级（兄弟）互不可管**（他们不在彼此的子树内）。
- "上级代管"不是单独规则，而是穿透的**自然结果**。

**项目层**同理：群主管**整个群**（成员 + 群声明）；无群主 → 老板。

## 6. 权限模型（写）

**员工 A 的写权限集 = 默认 ∪ 继承：**

1. **默认**：① `work/<A>/`（自己工作空间）；② A 作为管理者时，其**子树内**的部门声明与人声明（`department.json` + `*.agent.json`）。
2. **继承**：所有祖先部门 `department.json.permissions` 的路径（沿链累积）。
3. **本人额外**：`A.agent.json.permissions`。

**硬规则：**

- **人不可写任何 `*.agent.json`（含自己的）**——防"自授权"的唯一防线（管理者的写入是"写下级"）。
- **`permissions` 字段写入 = attenuation**：任何人写 `department.json.permissions` / `*.agent.json.permissions` / 群声明的 `permissions` 时，**值 ⊆ 写者当时的写权限集（含继承）**。
- **读**：零限制（D14）。

**与现有机制的关系：**

- 现有员工级 `permission.json` → `agent.json.permissions`；现有项目级 `permission.json` → 群声明 `permissions`。
- `request_permission`（员工申请 → 老板批准 → 框架代写）**保留**；框架/老板写入不受 attenuation 限制。新增：**主管/群主可直接写下级声明的 `permissions`**（受 attenuation）。

## 7. 作用域链与能力合并

**作用域链（会话装配时，从外到内）：**

```
系统 → 空间 → 项目（若在群里） → 组织链（该发言人的部门链，根→叶） → 员工
```

**各能力类型的合并语义（草案）：**

| 能力 | 现规则 | 目标规则 |
|---|---|---|
| `prompt` | 叠加 | 沿链**全部叠加**（顺序待定） |
| `skills` | 去重 | 去重，**近者优先**（优先级待定） |
| `mcp` | 同名窄者胜 | **同名近者胜**（优先级待定） |
| `permissions` | 累积 | 沿链**累积**（受 attenuation 约束） |

> **⚠️ 待定（用户明确暂缓）**：**能力覆盖优先级**——`prompt` 的叠加顺序、`skills` / `mcp` 里「组织链 vs 项目 vs 员工」谁赢——**不在本设计内定**，实现前另行讨论。

## 10. 待定 / 风险

- **能力覆盖优先级**（§7）：`prompt` 叠加顺序、`skills`/`mcp` 的层级胜负——**用户明确暂缓**，实现前定。
- **声明落点与文件名**：空间声明放哪、叫什么；项目成员名单存 `project.json` 字段还是保留 `members.md`。
- **`skills` 引用语法**：按名解析到 `openstaffs/skills/` 还是支持路径 / 外部 `skillPaths`。
- **`mcp` 内联形态**：内联 server 定义 vs 按名引用空间 `mcp.json`。
- **系统作用域声明**：框架内置的 prompt 模板如何并入"统一声明"（是否引入 `src/` 下的声明文件）。
- **`AGENTS.md` 移除的兼容**：Pi 祖先链自动加载消失，需确认"私活"场景 instructions 注入路径覆盖完整。
- **迁移**：P3 需一次性迁移脚本；不做双读。
- **项目 / 群聊**：本设计只加了"群主 + 统一声明"，群内模式（组队、`@` 语义等）未动——若后续重构，组织模型已与项目解耦，便于替换。
- **新增想法（未定稿，2026-10-19）**：头像字段、MCP 全局定义按名引用、项目/部门多主管——见 **§11**。
