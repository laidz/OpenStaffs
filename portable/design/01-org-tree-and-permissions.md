# 组织树与权限（可迁移的设计结论）

> 提炼自 `docs/superpowers/specs/2026-10-18-agent-org-hierarchy-design.md` 与
> `docs/superpowers/specs/2026-10-16-openstaffs-permissions-design.md`。
> 这里只留**换任何平台都成立**的结论，不依赖 OpenStaffs 的实现。

## 1. 组织树 = 文件系统

- **文件夹 = 部门**，可任意嵌套；**一个员工的档案 = 该目录下的一个配置文件**（`<名字>.agent.config.json`）。文件名主干就是 id，**全局唯一**。
- 部门自己的声明是**同级**的一个文件（`department.config.json`）：展示名 + 负责人（`head`）。
- 收益：组织图不需要画、不需要存库、不需要 UI 维护——`ls` 就是组织图，`git` 就是组织变更史，整个办公室可以 `tar` 走。

## 2. 权限 = 工具 × 路径（不是角色 × 权限）

这是整套设计的核心取舍：**不给角色配权限，给每个工具配路径表**。

```json
{ "permissions": { "write": ["./proj-a"], "read": ["./"], "bash": ["./proj-a"] } }
```

- 相对路径相对**该配置文件所在目录**解析 → 配置搬到哪，语义跟着走，不会失效。
- 落盘路线**只有两层**（项目 + 员工），两层**累加**，没有覆盖、没有优先级。少一层就少一类"到底哪个生效"的争论。
- `write` 一张表同时管 `write` 与 `edit`（语义相同的东西不拆两张表）。

## 3. 运行时授予 > 配置授予

三类权限**不写进任何配置文件**，运行时现算：

1. **私人目录** `work/<我>/` —— 对所有工具可用（每个人的工作产物天然隔离）；
2. **技能库** —— 只读（能力来自技能）；
3. **主管对自己部门子树** —— 写权限，**不跨兄弟部门**（`head` 只能写本级直属成员，写错视为无）。

配套硬规则：**`*.agent.config.json` 是硬保护，任何人（含主管）都写不了**——含自己的。理由：员工能改自己的权限 = 自授权，整套权限体系当场失效。改定义只有两条路：负责人手写，或授权流程**只代写发起者自己的 `permissions`**。

## 4. bash 是软边界，必须明说

`bash` 的路径检查是**近似检查**（`cd` + 裸文件名即可绕过），**不是沙箱**。设计上宁可诚实标注"软边界"，也不要假装它是沙箱——否则使用者会拿它当安全边界做承诺。

## 5. 越权要有一条正路

超出有效集时，唯一的正路是**异步申请**：`request_permission(tools[], paths[], reason)` → 立即返回 → 负责人在 UI 弹框里批准/拒绝 → 结果以新消息通知。

三条防滥用的约定：
- **一次说清**：同一组目录的多种权限一次列全（弹框按「人 × 会议 × 组目录」合并）；
- **等的时候别越狱**：不得用 bash、改写配置、请同伴代写绕过；
- **别原地轮询**：该干的活继续干，等通知。

## 6. 迁移到其他平台时

- Claude Code / Codex：目录结构可以直接类比成 repo 里的 `agents/` + 每人的 `AGENTS.md`；
  "按工具 → 路径"的权限表**没有直接对应物**，最接近的是 sandbox / allowlist 配置（粗粒度）——这是 OpenStaffs 里最难照搬、也最值钱的一块。
- 主管穿透、定义硬保护、异步授权这三条，任何多 agent 平台都得自己补一层，写在 prompt 里是不够的。
