# 会话与消息模型（可迁移的设计结论）

> 提炼自 `docs/superpowers/specs/2026-10-26-session-title-design.md`、
> `docs/superpowers/specs/2026-10-16-openstaffs-architecture-design.md` 与 `docs/superpowers/plans/2026-10-26-meeting-layer.md`。

## 1. 三层对象，别混在一起

| 对象 | 是什么 | 归谁 |
|---|---|---|
| **会议（meeting）** | 一次"为什么要聊"的容器（私聊 1:1 / 群聊 1:N） | 消息库一行 |
| **会话（session/conv）** | 某个成员在一场会议里的**独立上下文** | 会话表一行，`(meeting, member) → convId` |
| **消息（message）** | 一次投递的内容 | 消息表一行，属于某场会议 |

关键结论：
- 一个群会议里，**每个成员各有一条自己的会话**（各自上下文，互相不可见）。
- 会议**没有"结束"**：同一主题可以有多场会议，全部随时可继续聊；"新建会议"只是**再开一条线程**。
- 老板可删除整场会议（连带消息 / 会话映射 / 图钉），**agent 没有这个权限**。

## 2. 会话解析必须只有一个入口

`(room, member) → convId` 只能由**一个函数**决定（OpenStaffs 里是 `resolveSession`）：
有活跃行且能 attach → 复用；否则新建并登记。

老板发消息、授权结果投递、群回复触发、agent 主动 `send_message`/`new_session`——**四条路径全走它**。
任何一层自己拼"我在哪个会话"，就会在重启、并发、撤回时出现灵异 bug（历史教训：重启后漏补访问上下文，工具全部被拦，看起来像模型坏了）。

## 3. 会话的唯一真相是一张表

- 一行 = 一个会话：`convId / room / memberId / kind / started / ended / previous / 标题字段`。
- 约束：同一 owner 同时只允许**一条** `ended IS NULL`（事务保证）。
- 曾经的"会话链 markdown 文件"全部退役，启动时一次性导入。
- 重启恢复 = **一条 SQL**（`listActive()`）→ 逐个订阅，不再遍历"人 × 项目 × 链文件"。

## 4. 消息库只服务"会议视图"

- 会议视图读**自有库**（meetings + messages + sessions），**不读各成员的 transcript**。
- transcript 只服务"某条会话的原文/上下文"这一个调试端点——职责分开，互不牵连。
- 图钉（pin）= 负责人自己的待办标记：**不是未读**，打开会议/有人发言都不会自动清零。

## 5. UI 的输入侧语义（容易被忽略但很关键）

- **"新建会议"只置就绪态**：不落盘、不建会议；真正的创建发生在**第一条消息投递时**——空点不产生空会议，撤回也不产生。
- **正在跑时新消息排队**，显示为灰底"排队中"，可**单条撤回**（只撤还没开始投递的）；停止正在跑的任务用**中断**（会议级：同时停掉这场会议里所有在跑的成员）。
- **前端live流式气泡按"成员"清，不按 convId 清**——正式消息来自库行视图，两者的键不同源；按 convId 清会留下截断残影气泡。
- **SSE 事件名集合必须用类型钉死**（如 `Record<ServerEvent["type"], true>`）：服务端改事件名而前端订阅名单没跟上，表现为"回复不进聊天框"，且没有任何报错。

## 6. 模型退化护栏（loop guard）值得抄

真实事故：模型在"准备发多个工具调用"时卡死，正文把「Emit. / Output. / 现在.」重复到 19KB、57 秒，既污染历史又触发不了工具。

保守判定口径（**只看最后 200 行非空文本里同一行的重复次数**）：
- 重复行 ≥ 25 次，**且**占窗口 ≥ 25% 才判退化——避免把正常日志/表格分隔线误判。
- 两处生效：**流式阶段**命中即 abort 并广播失败；**落库阶段**再兜底丢弃，不写库、不触发 @。
- 新 run 开始清空检测状态，避免跨轮误伤。

> 结论：**这是 prompt 约束不了的模型退化，必须在运行时兜住。**任何把 agent 放进无人值守流程的产品都需要这一层。
