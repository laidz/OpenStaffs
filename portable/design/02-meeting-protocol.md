# 群聊协作协议（可迁移 · 这是最值钱的一份）

> 提炼自 `src/skills/openstaffs/SKILL.md` 与 `src/prompts/group.md`，
> 都是在真实开会里被踩出来的规则。**换任何多 agent 平台都能直接照抄。**

## 0. 前提：为什么需要协议

多个 agent 在一个共享频道里，默认行为会退化成三种灾难：
**互 @ 死循环**、**所有人都向老板汇报同一件事**、**各自猜任务背景**。
下面的每条规则都对应一次真实翻车。

## 1. `@` 只在消息最开头生效

- 只有**开头**的 `@成员` 会真的唤醒对方；正文中/结尾的 `@` 只是普通文字。
- 要 @ 多人：`@A @B` **全写在开头**。
- 每人任务不同：**拆成多条回复**，每条开头只 @ 一个对象（第二条起也要以 `@` 开头）。
- 没写 @ 的群回复视为**发给负责人**（系统补 `@老板` 前缀）。

> 这条是整个协议的地基：它把"谁该醒"变成一个可从文本**确定性解析**的问题，不依赖模型自觉。

## 2. 谁拉起，谁汇报（硬规定）

- 派活人是**同伴** → 完成后 `@同伴` 回告，由他汇总。
- 派活人是**负责人** → 直接 `@负责人` 交结果。
- **同一条任务链只有一个人向负责人交最终结果**，绝不允许两个人各总结一遍。

## 3. 协作过程中不 @ 负责人

同伴之间互 @ 的内容，负责人在群里**直接就能看见**，不需要再单独 @ 他汇报一遍。
`@负责人` 只留两个用途：**要拍板/资源/权限**，以及**交最终结果**。

## 4. 派活一次说完 + 自报身份

- 背景、目标、产出位置、验收标准写进**同一条**消息——每一条都是一轮唤醒，挤牙膏式提问会把成本乘三。
- 正文第一句自报身份：`我是 <名字>（<id>）；请你……；完成后 @我 回告`。
- 原因：**接任务的人只看得到这一条投递**，看不到发起人之前的上下文。

## 5. 看不见整场会议 → 允许主动补上下文

"你只看得到投递给你的消息"是刻意的隔离（成本与隐私）。
所以：背景不清时**先用 `meeting_history` 读本会议记录或 @发起人 问清，不要凭空猜**。

## 6. 防互 @ 死循环的收口

- 非必须不主动 @ 别人（@ = 派活 = 真花钱）。
- 被 @ 后**直接干活，不回"收到/好的"**。
- **来回两三轮没收敛就停**：写文件 + 给派活人一次性小结。
- 完工必须回告派活人（这条不能省，否则任务链断在半路）。

## 7. 大内容走文件，聊天只发摘要

聊天里只留「一句话结论 + 文件路径」；长报告、代码、日志、清单走工作目录里的文件。
理由有三：上下文成本、可追溯、以及避免大段内容污染其他人的视野。

## 8. 迁移时的最小可运行子集

如果要在一个新平台上重新实现，按这个顺序做，每条都能独立见效：

1. 开头 `@` 才触发（确定性解析）+ 没 @ 视为发给负责人；
2. 谁拉起谁汇报（一条链只有一个出口）；
3. 派活说明必须含"背景/目标/产出/回告对象"；
4. 允许用历史查询补上下文；
5. 两三轮不收敛就停。
